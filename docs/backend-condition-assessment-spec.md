# Spec: `condition_assessment` in backend report payloads

**Handover doc** for `estima-sk-backend` and `estima-backend` (this repo cannot
modify them). Goal: live PDFs rendered through `REPORT_SERVICE_URL` delegation
show the condition table **and the renovation-score hero** that the estima
template renders since report-service commit `a32a00c`.

## What report-service accepts

Optional top-level payload key, ignored when absent (report renders fine
without it — omit rather than send empty):

```json
"condition_assessment": {
  "available": true,
  "source": "Orientačné vyhodnotenie z fotografií inzerátu (Ollama gemma3:27b)",
  "overall_score": 65,
  "overall_label": "Čiastočne renovovaný",
  "score_positives": ["Moderná kuchynská linka", "Kúpeľňa po rekonštrukcii"],
  "score_negatives": ["Časť záberov je vizualizácia", "Nedokončené steny na chodbe"],
  "items": [
    {"element": "Podlahy", "state": "Rôzne", "note": "Laminát aj drevo, …"}
  ],
  "summary": "2–3 vety; pri vizualizáciách odporučiť obhliadku."
}
```

Field notes:

| Field | Type | Rendering |
|---|---|---|
| `available` | bool | gate — `false`/missing hides the whole block |
| `overall_score` | int 0–100 | hero number + meter bar; hero hidden when null |
| `overall_label` | str | bold state line in the hero (e.g. "Po rekonštrukcii") |
| `score_positives` / `score_negatives` | list[str] | "raises/lowers the score" bullets, 2–4 each |
| `items[]` | element/state/note | the condition table |
| `summary` | str | callout under the table |
| `source` | str | provenance footnote — always name the model/author |

Language of all strings must match the payload's `options.language`
(sk for estima.sk, cs for estimacz.cz).

## Where it goes in the backends

`src/services/reports/payload.py::build_payload` — add the block to the dict
when enrichment data exists for the property. Everything else (template,
delegation, fallback) already works; `_render_via_report_service` sends the
payload as-is.

## Where the data comes from

The content is **model- or human-authored upstream** — never derived from the
pixel metrics (that boundary is load-bearing; report-service's guardrail test
forbids semantic claims from `vision_analysis`). Options, in order of effort:

1. **Showcase-only (recommended first step):** store the enrichment for pinned
   listing 416 (generated by `scripts/evaluate_photos_ollama.py` in this repo —
   see `samples/sample_kosice_odborarska.ollama.json`) as a static JSON the
   backend loads for that property id. Users immediately see the full model
   example on /analyzy.
2. **Offline batch:** run the script (batch mode: multiple payloads per
   invocation) on a Mac with Ollama against exported payloads, then import the
   `condition_assessment` blocks into a backend table keyed by property id.
   The VPS has no GPU — do not attempt to run Ollama there.
3. **Live enrichment service:** out of scope for now (would live in
   estima-vision, keeping the no-cloud-AI rule).

## Prompts / schema to reuse

`scripts/evaluate_photos_ollama.py` in this repo — `LANGS["sk"]` /
`LANGS["cs"]` prompt packs and `CONDITION_SCHEMA` (Ollama structured outputs).
Reuse them verbatim so backend-produced assessments match the report wording.

## Acceptance criteria

- [ ] SK: `GET /reports/properties/416/pdf?lang=sk` (delegated) renders the
      hero (score + label + drivers) and the condition table
- [ ] CZ: same for the estimacz showcase property with `lang=cs`
- [ ] Properties without enrichment: block omitted, PDF renders unchanged
- [ ] `source` names the generator (model or "agent review") in every payload
